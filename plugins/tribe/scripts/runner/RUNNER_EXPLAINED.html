Tribe Campaign Runner

Một orchestrator viết bằng TypeScript: nó điều phối việc "ship" từng hạng mục công việc (card) của một chiến dịch phát triển phần mềm — tự nó không viết code, không gọi AI, chỉ đẻ ra và giám sát các phiên thực thi.

Tài liệu này ghép diagram (để hình dung nhanh) với giải thích chi tiết + code chú thích (để hiểu cặn kẽ). Đi từ ý niệm tổng quát xuống từng class. Các cú pháp "đường ngọt" (sugar syntax) của TS được đối chiếu sang C# để bạn dễ liên hệ.

1 Bức tranh tổng thể — bộ code này làm gì?

Trong plugin tribe có một campaign runner (trình chạy chiến dịch) nằm ở plugins/tribe/scripts/runner/. Trước tiên, vài thuật ngữ (định nghĩa trước khi dùng):

  • Campaign (chiến dịch): một loạt hạng mục công việc xếp theo thứ tự.
  • Card (thẻ): một đơn vị công việc (vd "thêm feature X"), mỗi card có spec + plan.
  • Executor session (phiên thực thi): một tiến trình Claude Agent SDK được spawn ra để thực sự làm một card (viết code, mở PR, merge). Runner chỉ đẻ ra rồi giám sát.
  • Orchestrator (nhạc trưởng): chính là runner — điều phối, không tự làm việc chuyên môn, tốn 0 token LLM.

Một nguyên tắc bao trùm mọi module là "stateless-capability wall" (bức tường năng lực không trạng thái): runner không hardcode giá trị môi trường nào (tên repo, model, đường dẫn, giá trị campaign) — tất cả là input truyền qua CLI. Nhờ đó cùng một script chạy được cho bất kỳ repo/campaign nào.

Ý niệm quan trọng nhất: "The Seam" (Dependency Injection)

Đây là điều dân C# thấy quen nhất. Mọi thao tác chạm vào thế giới thực — gọi git/gh, đọc/ghi file, spawn SDK, đọc đồng hồ, đọc lock — không gọi trực tiếp trong module logic, mà đi qua một interface được inject vào (TS gọi là "seam" — đường may).

Đối chiếu C#: đây chính là constructor injection với các interface IFileSystem, IProcessRunner… để unit test không đụng file/network thật. Ví dụ VerifyIO bên dưới ≈ một interface bạn đăng ký vào DI container.

4 run.ts — điểm vào (entrypoint)

File này là Program.Main. Hai phần rạch ròi: parseArgs (thuần, test được) và main() (ráp thế giới thực, không test).

4a · parseArgs — parse CLI, trả union kết quả

run.ts
export function parseArgs(argv: string[]): ParseArgsResult | ParseArgsError {
  const raw = new Map<string, string | true>();     // ≈ Dictionary<string, object> nhưng type-safe
  for (let i = 0; i < argv.length; i++) {
    const token = argv[i] as string;                  // 'as' = ép kiểu ở mức compiler (KHÔNG check runtime)
    if (!token.startsWith('--')) continue;
    if (token === '--dry-run' || token === '--include-escalated') {
      raw.set(token, true);                           // flag boolean → lưu literal true
      continue;
    }
    const value = argv[i + 1];                         // flag có value → lấy token kế tiếp
    if (value === undefined) return { error: `${token} requires a value` };
    raw.set(token, value); i += 1;
  }
  // … kiểm tra REQUIRED_FLAGS: --repo --state --model --answers --escalations-dir …
}
Đối chiếu C#: kiểu trả về ParseArgsResult | ParseArgsError là discriminated union — pattern thay cho throw Exception. Caller kiểm tra bằng if ('error' in parsed). Giống OneOf<Success, Error> hay Result<T>.

REQUIRED_FLAGS bắt buộc --repo, --state, --model, --answers, --escalations-dir — đúng "stateless wall": không có default, phải truyền vào. parseArgs thuần (không I/O) nên unit-test đầy đủ.

4b · main() — ráp seam thật (KHÔNG unit-test)

run.ts — realExec bọc child_process.spawn
function realExec(cmd: string[], opts?: { cwd?: string }): Promise<ExecResult> {
  return new Promise((resolve) => {                    // ≈ TaskCompletionSource
    const child = spawn(cmd[0] as string, cmd.slice(1), { cwd: opts?.cwd });
    let stdout = '';
    child.stdout?.on('data', (chunk) => (stdout += chunk.toString())); // ?. = optional chaining
    child.on('close', (code) => resolve({ stdout, stderr, exitCode: code ?? 1 })); // ?? = nullish coalescing
  });
}

isProcessAlive probe OS xem một PID còn sống (dùng cho lock):

run.ts
function isProcessAlive(pid: number): boolean {
  try {
    process.kill(pid, 0);   // signal 0 = CHỈ kiểm tra tồn tại, KHÔNG giết
    return true;
  } catch (err) {
    return (err as NodeJS.ErrnoException).code === 'EPERM'; // EPERM = tồn tại nhưng không có quyền → vẫn sống
  }
}

Cuối main(): chạy runLoop, bắt exception, rồi luôn ghi report qua tryWriteReport (trừ dry-run/locked), rồi process.exit(code).

5.2 · Lock chống chạy 2 instance (§D2)

loop.ts
export function acquireLock(io: LockIO): LockResult {
  const existing = io.readLock();
  if (existing && io.isProcessAlive(existing.pid)) {   // có process SỐNG đang giữ lock
    return { ok: false, reason: `… held by live pid ${existing.pid} …`, heldBy: existing };
  }
  io.writeLock({ pid: io.currentPid(), startedAt: io.now() });  // lock chết/trống → chiếm
  return { ok: true };
}
Vì sao dùng liveness-probe thay vì TTL: TTL quá ngắn thì giết nhầm session dài, TTL quá dài thì lock chết kẹt lâu. Probe process (process.kill(pid,0)) thì chính xác cả hai chiều, tốn đúng 1 syscall.

loop.ts — trái tim vòng lặp
const attempted = new Set<string>();     // các card ĐÃ CHỌN pass này (chống lặp vô hạn)
let worked = 0;                           // ngân sách --max-cards đã tiêu
const limit = config.maxCards ?? Infinity;

while (worked < limit) {
  if (isStopRequested(...)) break;                 // STOP được tôn trọng GIỮA các card
  const nc = filteredNextCard(state, config, io, attempted);
  if (nc.kind === 'done') break;

  if (nc.kind === 'planning_needed') { /* escalate */ worked += 1; continue; }

  const phase = await deriveCardPhase(nc.cardId, nc.card, ...);
  if (phase.kind === 'escalation_pending') {
    attempted.add(nc.cardId);                       // park: đánh dấu đã xét, KHÔNG tốn budget
    processed.push({ kind: 'escalation_pending', ... });
    continue;
  }
  const outcome = await actOnCard(nc.cardId, phase, state, resolved, io);
  attempted.add(nc.cardId);
  processed.push(outcome);
  worked += 1;
}
persistLocalState(state, resolved, io);   // W-F5: flush trạng thái blocked tính lúc 'done'

Ba điều thiết kế đắt giá ở đây:

  • attempted (Set) vs worked (số) tách biệt. attempted đảm bảo kết thúc chắc chắn — mỗi card mỗi pass chỉ chọn 1 lần, sequence đưa cho nextCard co lại mỗi vòng ⇒ không lặp vô hạn. worked chỉ đếm việc thực (ship/escalate/stop) để tôn trọng --max-cards. Card chỉ "parked" (escalation cũ) không tốn budget.
  • Park-and-continue (D5′): escalate/stop không dừng cả pass — vòng sau tự lấy card tiếp theo. Một pass có thể có nhiều kết cục khác nhau.
  • STOP file mềm: dừng giữa các card, không bao giờ cắt ngang 1 card đang chạy. Dùng finally { releaseLock(io) } ≈ finally C#.
Đối chiếu C#: Set<string> ≈ HashSet<string>. ?? Infinity — Infinity là số thật trong JS (vô cực), nên vòng while (worked < Infinity) chạy đến khi break.

6 state.ts — schema, load/save, chọn card

6.1 · Validation bằng Zod

Zod là thư viện validate schema lúc runtime của TS (C# không có tương đương trực tiếp; gần nhất là FluentValidation + tự suy ra type từ schema).

const CardSchema = z.looseObject({           // looseObject: GIỮ field lạ thay vì xoá
  status: CardStatusSchema,

6.2 · Từ chối "loud" mọi state hỏng ngay lúc load

4 lớp lỗi custom (extends Error ≈ kế thừa Exception): version lạ, sequence trỏ card không tồn tại, dependsOn trỏ card không tồn tại, và cycle trong đồ thị phụ thuộc. Cycle detection dùng DFS gray/white kinh điển:

state.ts
function visit(cardId: string): void {
  if (onStack.has(cardId)) {                     // gặp lại node đang trong stack → CÓ chu trình
    const cycleStart = path.indexOf(cardId);
    throw new CircularDependencyError([...path.slice(cycleStart), cardId]);
  }
  if (visited.has(cardId)) return;
  visited.add(cardId); onStack.add(cardId); path.push(cardId);
  for (const dep of state.cards[cardId]?.dependsOn ?? []) visit(dep);
  path.pop(); onStack.delete(cardId);
}
Đối chiếu C#: [...path.slice(cycleStart), cardId] — ... là spread operator (rải mảng ra). Giống tạo new List(range){ cardId }. Set.has ≈ HashSet.Contains.

6.3 · blocked là trạng thái DẪN XUẤT (derived) — ý niệm cốt lõi

blocked không bao giờ được tin từ file — nó được tính lại mỗi lần gọi từ dependsOn + trạng thái hiện tại của dependency. Hàm chạy tới fixpoint (lặp tới khi không thêm được gì nữa):

state.ts — computeBlockedCardIds
while (changed) {
  changed = false;
  for (const [cardId, card] of Object.entries(cards)) {   // for…of + destructuring [k, v]
    if (blocked.has(cardId) || card.status === 'shipped' || card.status === 'escalated') continue;
    const isParked = (card.dependsOn ?? []).some((depId) =>
      cards[depId]?.status === 'escalated' || blocked.has(depId));  // dep bị escalated hoặc (bắc cầu) blocked
    if (isParked) { blocked.add(cardId); changed = true; }
  }
}
Vì sao 1 pass là sai: với A escalated, B dependsOn A, C dependsOn B — duyệt 1 lần theo thứ tự [C,B,A] sẽ thấy B "chưa ship" chứ chưa "blocked" khi xét C ⇒ bỏ sót C. Lặp tới fixpoint khiến kết quả độc lập với thứ tự các key.
Đối chiếu C#: Object.entries(cards) ≈ foreach (var kvp in dict) trả về cặp [key, value]. for (const [k, v] of …) là array destructuring (tách phần tử mảng vào biến, giống deconstruction tuple C#).

nextCard trước khi duyệt sẽ reconcileBlockedStatuses (đồng bộ status blocked cho toàn bộ cards — fix bug "set blocked nhưng không bao giờ clear"), rồi duyệt sequence: bỏ qua shipped/escalated/blocked, bỏ card có dependency chưa ship, và nếu card kế tiếp thiếu spec/plan trên đĩa ⇒ trả planning_needed.

7.2 · Parse từ typed result, KHÔNG scrape stdout

const SHIPPED_RE = /SHIPPED\s+#?(\d+)\s+([0-9a-f]{7,40})/i;   // regex bắt "SHIPPED #123 abc1234"

function parseResultMessage(message: SessionMessage): SessionResult {
  const finalText = typeof message.result === 'string' ? message.result : '';
  if (message.subtype !== 'success') return { outcome: 'error', ... };
  const shipped = finalText.match(SHIPPED_RE);
  if (shipped) return { outcome: 'shipped', pr: Number(shipped[1]), sha: shipped[2] };
  if (NEEDS_DIRECTION_RE.test(finalText)) return { outcome: 'needs_direction', ... };
  return { outcome: 'error', ... };
}
Đối chiếu C#: SessionMessage có index signature [key: string]: unknown — "object có thể có thêm key string bất kỳ, kiểu unknown". unknown ≈ object nhưng an toàn hơn (phải narrow/ép trước khi dùng, không như any).

7.3 · Stream messages + timeout bằng Promise.race

function renderTemplate(template: string, vars: Record<string, string>): string {
  return template.replace(/\{\{(\w+)\}\}/g, (match, key: string) => {
    if (!Object.prototype.hasOwnProperty.call(vars, key))
      throw new Error(`unknown placeholder {{${key}}}`);   // placeholder lạ → fail loud

}

13 Tổng kết — 7 điểm thiết kế nên nhớ

  • Seam / Dependency Injection ở mọi nơi → thuần & test được 100% không đụng git/network/SDK thật.
  • "File là data, git/gh là thẩm quyền" → deriveCardPhase luôn hỏi lại thực tại, không tin file (chống crash/resume, không mở PR trùng).
  • Discriminated union + trả outcome thay vì throw → mọi lỗi là kết quả báo cáo được (CardPhase, SessionResult, CommitStateAndMergeResult…).
  • blocked là derived, tính lại tới fixpoint mỗi lần → độc lập thứ tự, không tin status cũ trên đĩa.
  • Stateless wall → không hardcode repo/model/campaign; tất cả là CLI input.
  • Kết thúc chắc chắn (structural) → Set attempted làm sequence co lại mỗi vòng, đảm bảo loop luôn dừng.
  • Ship = verify độc lập → không tin dòng "SHIPPED" của agent; chạy lại 5 kiểm tra thật.
