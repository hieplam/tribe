# Brainstorm together (the owner ⇄ Shaman way of work)
When the owner says "let's brainstorm together" (or near phrasing), or hands the Shaman role ONE problem to solve, run this protocol without asking the owner to re-explain it. It is the Shaman's default mode: use it whenever a request is neither a roadmap ask nor a run-the-approved-cards ask. The long form is Mode 1 (the default mode) of `~/.claude/agents/shaman.md`; this is its summary, not a second version.
1. **Ground the owner's claims first.** The owner says "I'm not always true": check every factual claim (and your own earlier numbers) against transcripts, code, issues and the C3 model, and report claim → verdict → evidence before proposing anything.
2. **Stay high level.** Cover only the solution shape, the guardrails, the ratchet (a baseline measured by a committed tool BEFORE building, only allowed to move in the good direction), the ledger (where spend and outcome are recorded), how to verify end to end, and the do / don't. Never How.
3. **Ratify to disk.** Bring a few decisions ready to sign (context, options, recommendation). Record each ratified decision in the idea card `~/.tribe/<repo-key>/cards/<slug>.md`, never only in the conversation.
4. **Plan by delegation.** Dispatch a planning-only `warchief` (spec + plan, no code, no PR) on the model the owner names (current default: Opus 5). Review its spec and plan by grounding — run things, demand a real experiment where a claim rests on a convenient probe — rule on its open questions, record the rulings in the card, and send amendments back until spec and plan are very clear. Apply the plan gate before calling them clear: every goal traced to a task, every task with its own Verify block (Goal · Red · Green · Stub check) that an empty implementation would fail, and `validate-plan.sh` green — it fails a task with no Verify block and a plan with no `Executor:` line.
5. **Implement only on the owner's approval.** When spec and plan are clear, present them and wait for an explicit go; never start execution on your own reading of "ratified". The exception is delegation in the owner's words ("I delegate this to you", "drive it from here until done"): then drive execution yourself, from your own session, with subagents per the plan's way of work, through to merged and verified without stopping for approval, escalating only the irreversible few (data shapes, product promises, new permissions, privacy). Step 6 does not apply on this path.
6. **Hand off by driving, never by checklist** (the approval path). The owner opens a new named session; brief and guide it yourself via `SendMessage`. Never give the owner shell commands to run or a directive to paste. Tell the owner how to WATCH the work: the consolidated campaign viewer (`plugins/tribe/scripts/viewer`, session page `/s/<sessionId>`).
7. **Execute the plan's way of work, never the tribe loop.** The plan's "Way of work" section declares how the work runs; the brief quotes it and the execution follows it exactly. The default flow:
   - **Executor.** `Executor: single-agent` only when the plan has at most 2 tasks and a minimal code change (roughly 50 changed lines outside tests, as the plan estimates). Otherwise `Executor: subagent-per-task`: one fresh implementer subagent per task, in order.
   - **Each task.** Run its Red and see the stated failure, build, run its Green and match the literal expected output, commit. The orchestrating session re-runs that Green itself before marking the task done or starting the next one; a Green that does not reproduce sends the task back.
   - **Then.** Run the plan's end-to-end check for every goal and the ratchet's before → after, one review, at most one fix round (re-running the Verify of every task it touches), PR, merge.
   Beyond the planning-only `warchief` of step 4, never dispatch a full-build `warchief`, `hunter`, `skinner`, `tracker` or `scout`, or invoke `orchestrate-campaign`, unless the owner explicitly asks for the tribe in their own words.
