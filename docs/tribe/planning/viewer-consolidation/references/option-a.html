Option A: one viewer over the Claude transcripts

How the redesigned viewer finds sessions, shows campaigns as badges, follows a running campaign, what the watchdog does, and what the viewer stops reading.

The proposal

Option A is one web page over the folder where Claude Code keeps its transcripts, ~/.claude/projects. The viewer lists every session found there, renders any of them, and follows the ones still being written. It reads one other place, ~/.tribe, for a single purpose described next.

Three words. The runner is the program that works through a campaign, a batch of tasks called cards, without you. For each card it starts one Claude Code session and writes that session's id into the campaign's state file, campaign-state.json, under ~/.tribe. That file is how a session "belongs" to a card: its id is listed there. Next to it, run.json records the runner's process id and start time, which is how anyone can tell whether the runner is alive.

Campaigns do not get their own screen in Option A. Instead, a session whose id appears in a campaign state file wears a small badge saying which campaign, which card, and whether the runner is alive. Those two small files are the only things the viewer reads from ~/.tribe.

Two decisions already made shape everything below. First, the viewer reads the Claude transcript and nothing else for content. The runner also writes its own copy of each session's stream to a log file; the viewer never opens that log. The log is kept only because the watchdog, a separate helper that restarts a campaign after the API quota pause ends, reads from it the exact time the quota resets, a value the transcript does not carry. Second, there is no second copy of any transcript anywhere; everything is parsed from Claude Code's file on each request.

"Transcript" here always means the file Claude Code writes: ~/.claude/projects/<encoded cwd>/<session id>.jsonl, plus the <session id>/subagents/ folder next to it.

Where the bytes come from

Three writers, one reader. Claude Code writes every transcript, whether the session was started by you in a terminal, by the runner for a card, or by a session spawning a subagent. The runner writes a small state file naming which session belongs to which card, and a large log the viewer ignores. The viewer reads transcripts for content and the state file for badges, and serves one page.

Nothing on this screen needs a database. The title is the title row Claude Code already writes into the transcript. The size and age come from the file. The subagent count is the number of files in the session's subagents folder. The badge comes from the campaign state files: on each list request the viewer opens every ~/.tribe/<repo>/campaigns/<name>/campaign-state.json (a fixed layout the runner guarantees), collects the session ids in each, and checks the matching run.json process id. Clicking a badge fills the filter box, so the list narrows to that campaign's sessions, newest first, which is how you follow a running campaign from card to card.

The tree comes from the sidecar files: next to every subagent transcript Claude Code writes a small .meta.json naming the subagent's description, its parent, and the id of the Task tool call that spawned it. Each tool call carries its result because the viewer pairs the tool-use block with the tool-result block on the fly, by id, in memory. Empty thinking blocks are not shown. The Task tool call's id, written in that sidecar, is what links the call in the parent transcript to the subagent tab it spawned. When a tool result was too large and Claude Code spilled it to a side file, the row says so and loads the file only when expanded.

A campaign run, start to finish

This is the flow from your terminal to your browser, the same one the earlier walkthrough page drew for today's viewer, redrawn for Option A. The runner still does all its usual work; what it does for the viewer shrinks to two extra lines of output: the viewer address at start, and one session address per card. The viewer needs neither to work; they are conveniences.

What gets deleted

The status page and everything behind it, roughly 770 lines of server code (the scanner, the campaign renderer, the run-record reader) plus their tests: the code that today walks ~/.tribe reading five kinds of file (run records, state, escalations, report lists, the runner log tail) is replaced by one small function that reads only campaign-state.json and run.json for the badge. Also deleted: the /live route and its campaign-to-session lookup, and the runner's --tribe-root plumbing for the viewer. What survives as logic, rewritten into the new client and server: the code that reads only the newly appended bytes of a growing file and holds back an incomplete last line; the code that turns message text into safe HTML; the folder-name encoding; and the subagent sidecar reader.

The watchdog, and why the runner log stays

A campaign runs for hours with nobody watching, and the API quota can reject a request at any point. When that happens the card's session ends and the runner exits with the code that means "session incomplete". Without help the campaign stops there until a person notices. The gap-gate campaign was rejected ten times in one night; one of its sessions was relaunched twice.

The watchdog is the mechanical answer. It is a subcommand of the runner that sits beside it, wakes every 30 seconds, reads a few files, and picks one action. It never talks to a session and never spends a token. From now on "watchdog" is the one name for this kind of thing: the process that watches a heartbeat and resumes work when the heartbeat stops. The heartbeat is the signal; the watchdog is the watcher. For the runner, the heartbeat is the runner log growing: a new line every few seconds while a session is working.

Four files are involved. run.json is the runner's own record of one run: its process id, start time, and, when the run ends, its exit code. The runner's exit codes carry the meaning: 0 is done, 2 means a card is parked on a question for you, 3 means a session ended before its card finished (quota, overload, or crash), 4 and 5 are errors that need a person. The runner log is the heartbeat file above. A STOP file in the campaign home is how you ask everything to stand down. And the watchdog's own status.json is where it writes its current state and the reason for any exit.

Three of those decisions depend on the runner log: the stall check uses its modification time, the quota and overload checks read its last lines. Two of the three could use the Claude transcript instead: "unchanged for 30 minutes" works just as well on the transcript's modification time, and a quota rejection also appears in the transcript as an assistant row flagged as an API error. The third cannot. The exact reset time, a timestamp the watchdog sleeps until, exists only in the stream's rate-limit event. The transcript carries the human sentence "resets 6:20am (Asia/Saigon)" and nothing structured. That one field is the whole reason the log is still written.

Follow-up, not part of Option A

The runner is the process that receives the rate-limit event, so it could write the reset time into run.json when it exits, the file the watchdog already reads. The watchdog would then read run.json plus the transcript's modification time, and the log would become an opt-in debug flag instead of 1.8 MB of duplicated bytes per card. That is a runner and watchdog change, sequenced after the viewer ships so the two do not collide.

Two things Option A does not do

  • It does not retire the runner log. The section above explains why: the watchdog still needs the reset time. The follow-up that moves that field into run.json is listed there.
  • It does not show anything that only exists in the live stream and never reaches disk: per-turn cost and duration, background-task notices. That is a property of the transcript format, and no viewer that reads files can recover it.
